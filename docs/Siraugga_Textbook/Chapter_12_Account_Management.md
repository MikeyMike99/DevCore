# Chapter 12: Account Management and Privilege Architecture

The central orchestrator of the DevCore ecosystem—acting as the ultimate Identity Provider (IdP)—plays a critical role in the security of the framework. In a Zero-Trust AI environment, determining *who* or *what* is interacting with the system is only the first step. The orchestrator must mathematically guarantee that every user, modder, and autonomous subagent possesses an account type strictly tailored to their operational role. 

This enforcement ensures that entities can only access and modify data on a strict "need-to-know" basis, drastically reducing the blast radius of a compromised agent or a malicious prompt injection.

For example, the central Siraugga Orchestrator issues the following primary account classifications:

*   **User Accounts (Tier 2 Modders & Tier 3 Developers):** Utilized for the day-to-day use of system resources. These accounts are jailed strictly to their assigned game project folders (e.g., `game_demo/`). They are permitted to build logic, write JSON states, and execute sandboxed code, but they are entirely blind to the overarching network.
*   **Service Accounts (AI Subagents & Daemons):** Specialized accounts utilized for automated interaction with the operating system. In DevCore, these are the individual autonomous AI agents. They are highly constrained, non-human accounts granted access to specific toolsets (like `write_to_file` or `run_command`) strictly for the duration of their lifecycle.
*   **Guest Accounts (Tier 1 End Users / Players):** Utilized for temporary, highly restricted users who only need to interact with the final compiled application or in-game NPCs. They have absolutely no write access to the underlying logic.

Proper management of these accounts and permissions is the bedrock of securing sensitive information and maintaining the integrity of the live game state.

## Agentic Account Types and Identity Profiling

A fundamental rule of the Siraugga framework is that organizations must **never share accounts** for privileged users, administrators, or AI applications. The administrator account (Tier 5) must only be used to administer the core system (`TIER_CORE_ENGINE`). If a Tier 5 Super Admin were to recklessly use their root account to test an untrusted, malware-infected AI plugin from a community forum, the entire organization—and every connected game server—would be compromised.

Tier 4 App Admins and Tier 5 Super Admins must be intimately aware of the default group and user accounts that are generated by the underlying operating system or standard LLM wrappers. Because cybercriminals and rogue modders are deeply familiar with default configurations and predictable API endpoints, leaving default guest or admin accounts active is an unacceptable security risk. To harden the infrastructure, administrators must replace all default accounts, enforce cryptographic token validation, and disable any inactive agent profiles immediately.

As the Identity Provider (IdP), the DevCore central server is responsible for authenticating the identity of every connection. When a new Tier 2 Modder joins the project, the orchestrator executes a rigid onboarding sequence:

1.  **Identity Profiling:** Creating a localized, cryptographic identity profile for the user.
2.  **Hardware Registration (FAIM):** Registering the Modder’s physical computer and mobile devices, binding their access tokens strictly to their authorized hardware to prevent session hijacking.
3.  **Lifecycle Management:** Disabling or deactivating any accounts that are no longer needed, and purging organizational data from the user’s sandboxes.

### Spatial and Temporal Access Restrictions
To enforce absolute control over the swarm, administrators utilize temporal and spatial restrictions:
*   **Time-of-Day Restrictions:** Controlling precisely when a Modder or a specific AI swarm can log in (e.g., locking out AI compilation tools during peak player hours to save API bandwidth).
*   **Geofencing (Sandbox Confinement):** In traditional IT, geofencing triggers actions when a user crosses a geographic boundary. In DevCore, Geofencing translates directly to **Sandbox Path Confinement**. If a Tier 3 subagent attempts to execute a tool outside its assigned `cwd` (Current Working Directory), the geofence triggers an immediate `PermissionError` and alerts the Admin.
*   **Geolocation (Hardware Locking):** Identifying a Modder based on their physical network location and hardware signature, ensuring they are not connecting from an unauthorized proxy.
*   **Geotagging (Semantic Watermarking):** Adding an identifier to an artifact based on its origin. In DevCore, every generated line of code or JSON file is "geotagged" with the unique UUID of the specific AI agent that created it, ensuring absolute accountability.

## Securing Privileged Accounts

Cybercriminals heavily target privileged accounts (Tier 4 and Tier 5). Because these are the most powerful accounts in the organization—possessing elevated, unrestricted access to deploy game engines, orchestrate raw Linux operating systems, and modify network devices—they are the holy grail for attackers. 

If a threat actor successfully executes an **Agentic Jailbreak** (overwriting a privileged AI’s System Prompt to steal its root access), they gain absolute control over the logic mainframe. To prevent this, organizations must adopt robust, uncompromising practices for securing privileged accounts:

*   **Identify and Reduce:** Audit the system and minimize the number of Tier 5 Admin accounts. Not everyone needs root access.
*   **Enforce the Principle of Least Privilege:** Users, subagents, and daemons must *only* have access to the specific resources (networks, JSON states, and files) absolutely necessary to perform their assigned function. A `QA` agent should not have the ability to modify the server configuration.
*   **Immediate Revocation:** Revoke access rights and kill active AI subprocesses the instant an employee leaves, a Modder goes rogue, or an agent completes its task.
*   **Eliminate Shared Credentials:** Never allow multiple Tier 4 Admins to share a single API key or SSH login.
*   **Automated Rotation:** Automatically rotate privileged account passwords, API keys, and cryptographic tokens every 30 to 60 days.
*   **Record Privileged Sessions:** Every action taken by a privileged AI agent must be meticulously recorded. DevCore accomplishes this by writing immutable **Transcript Logs** (`transcript.jsonl`), preserving the agent's full chain-of-thought and terminal output for forensic auditing.
*   **The Clean Workspace Protocol (Embedded Passwords):** Administrators must implement strict processes to eliminate embedded passwords in scripts or service accounts. In DevCore, this is enforced via the **Clean Workspace Protocol**: AI agents are strictly forbidden from leaving single-use scratch scripts or `.env` files behind. Configuration files containing secrets must be purely ephemeral and deleted immediately after use.
*   **Generate Anomaly Alerts:** The **Raugus Resolver** must continuously monitor the swarm, generating immediate alerts for unusual behavior (e.g., an agent burning an abnormal amount of tokens or typing with a suspicious terminal rhythm).
*   **Multi-Factor Authentication (MFA):** Enforce multi-factor cryptographic validation for all administrative access.
*   **Implement a Gateway:** Place a rigid gateway (The Zero-Restart Web Portal) between the end-user and the sensitive assets, completely isolating the core network from malware or malicious prompt injections.

Continuously securing and locking down these privileged accounts is critical to the survival of the DevCore framework.

## File Access Control

Permissions are the structural rules configured to limit folder or file access for an individual user or AI agent. Following the principle of **least privilege** and "need-to-know" access, entities must be mathematically restricted to only the resources they require. 

For example, a Tier 2 Modder should never be granted read/write access to the entire root directory simply because it is easier to configure. Doing so creates a catastrophic vulnerability; if the Modder's local environment becomes infected, the cybercriminal instantly gains access to the entire server drive.

In the Siraugga framework, File Access Control is violently enforced through the **Five File Classification Tiers**:

1.  **`TIER_SAFE_WORKSPACE`:** The general premises. Game scripts, NPC JSON data, and local assets. Accessible to Tier 2 Modders and Tier 3 Agents.
2.  **`TIER_CORE_ENGINE`:** The server and orchestration scripts (`server.py`, `agent_manager.py`). Highly sensitive. Restricted exclusively to Tier 5 Super Admins.
3.  **`TIER_ADMIN_LOG`:** Daemon logs and transcripts. Read-only access for Admins to monitor the system without altering historical truth.
4.  **`TIER_FORBIDDEN`:** The absolute void. Virtual environments (`venv/`), Git internals, and path-traversal escapes. Hard-blocked for all roles, including Admins, to prevent accidental system destruction.

By routing all read/write requests through strict path resolution modules (`resolve_safe_path()`), the orchestrator guarantees that any attempt to traverse outside an assigned folder boundary results in an immediate, localized lockdown.
